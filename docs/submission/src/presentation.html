GlucoTwin v0.21

Problem and healthcare use case

Condition: Type 2 diabetes (India)

  • Post-meal glucose excursions are common in T2D, and a clinician reviewing CGM usually sees them after they happen.
  • The challenge asks for a twin that fuses simulated EHR with wearable / CGM streams and predicts an adverse event, e.g. "a sudden glucose spike 2 hours in advance".

Use case

  • A doctor monitors several remotely monitored patients.
  • The twin flags who is likely to cross 180 mg/dL in the next 2 h, while glucose is still normal, with a forecast band and the reasons.

Event definition (frozen before modelling)

At time t, asked only if the latest CGM ≤ 180 mg/dL. Positive if ≥ 3 consecutive 5-min CGM readings > 180 mg/dL (≥ 15 min; gaps break the run) begin within (t, t + 120 min].

Why "onset": predicting "above 180" while already above 180 is trivial and useless clinically.

Outputs per CGM reading

  • Glucose forecast at 30/60/90/120 min with an 80% interval
  • Probability of excursion onset within 2 h, alert at a validation-chosen threshold
  • Grouped explanation (associations, not causes)

Why a digital twin, and not a single risk score?

Continuously updated

A versioned per-patient state is updated with every observation: glucose and trend, 24 h time-in-range, meals and carbs on board, activity, data quality. Forecasts are re-issued at each reading.

Fuses record + streams

The static record (labs, medications, history) gives context and a prior. Streams give the current state. Both feed the same leakage-safe feature builder offline and online.

Personalised

Each twin learns its patient's carb sensitivity (mg/dL per g) from observed meal responses, shrunk towards a record-based prior. This changes the expected post-meal rise.

What it is not (yet)

The twin does not simulate physiological interventions such as activity ("what if she walks after lunch?"). That would need per-patient physiological parameter fitting, which is on the roadmap, not built. Its what-if meal lab only re-runs the learned forecasters on a hypothetical meal (an association, not a mechanism). Our twin is a state-tracking forecaster with one personalised physiological parameter.

Data: synthetic, by rule and by necessity

  • Rules: "strictly required to use anonymized, open-source, or synthetic datasets".
  • Real CGM + EHR datasets with 5-min data (OhioT1DM, T1DEXI, DiaTrend) need data use agreements, which is not feasible before the deadline.
  • Generator: a Bergman-type minimal model with meals, activity, dawn effect and unobserved "stress days". Hidden physiology is never shown to models.
  • Observable: record (labs derived with noise), CGM with lag, bias, AR noise and dropouts, steps, heart rate, meal logs with carb error and 10% unlogged.
  • 60 patients × 14 days; 5-min CGM; seed 20261017.

Evaluation protocol and leakage safeguards

Protocol

  • Patient-level split 36 / 12 / 12; no patient appears in two splits.
  • All models are fitted on train only. Model choice, alert threshold and conformal intervals use validation only. Test is evaluated once.
  • Baselines on the identical test rows: persistence, damped trend, ridge (trajectory); trend rule (event).
  • Deterministic: a clean clone with a fresh environment reproduced every metric exactly (wave-2 audit).

Leakage safeguards (tested)

  • Features use observations ≤ t only. A truncation test shows that removing the future never changes past features.
  • The same code builds features offline and online (parity test).
  • Personal carb sensitivity uses a meal only after its 2-h response window has ended.
  • Mutation check: injecting a 30-min future shift makes two leakage tests fail.
  • The dashboard replay can only show held-out test patients and never reveals data after "now" (API test).

Clinician dashboard: what the doctor sees

  • Patient list: held-out test patients, latest glucose, latest risk.
  • Record header: labs, medications, history.
  • Glucose chart: last 12 h, 2-h forecast with 80% band, meals, earlier predictions versus what happened.
  • Risk card: probability (never shown as 100%), alert wording "Consider reviewing", top factor groups.
  • Risk history and twin state: TIR, carbs on board, learned carb sensitivity, data quality.
  • Replay: the twin only sees data up to "now".
  • Evaluation tab: every baseline and limitation.
  • What-if meal lab (simulated): X g eaten now versus a zero-carb meal at the same time, plus a grey no-meal comparison. Learned model associations, not physiology; meals under 30 g flagged unreliable.

Safety boundaries and limitations

Safety boundaries (built in)

  • A "synthetic, not a medical device" banner on every screen; synthetic IDs (SYN-####) and names tagged "(synthetic)".
  • No instructions: the alert text is "Consider reviewing", never "give insulin" or "eat".
  • Explanations and what-if meal results are labelled as associations, not causes; a what-if is never written to the record.
  • No risk number when data are insufficient or stale; no onset risk when glucose is already above 180.
  • Probabilities are never displayed as 100% or 0%.
  • Local demo: no authentication, so it is not for real patient data.

Limitations

  • Evaluated only on our own simulator; no real-patient or external validation.
  • 12 test patients, so the confidence intervals are wide.
  • Meal logging is near-real-time in the main cohort, which is optimistic.
  • Lows are under-represented (0.37% of readings < 70 mg/dL vs 2.4% published); the low-glucose watch is a lower bound, not a probability.
  • Vs simulator ground truth, the What-If underestimates late meal effects (+120 min MAE 29.0 vs 12.8 mg/dL for a cohort-average curve).
  • Personalisation is shown only in simulation (hidden meal gain recovered, r 0.95 by day 3; +30 min RMSE −0.52 mg/dL, 95% CI 0.12–0.96).
  • No HRV or sleep streams; genotype is synthetic and display-only. No regulatory claims (CDSCO SaMD, DPDP, HIPAA).

Potential impact and the path to real validation

If validated, the intended value is

  • Earlier, reviewable warnings for remotely monitored T2D patients, in place of after-the-fact CGM review.
  • A per-patient view that explains why risk is high (meal, trend, recent control).
  • A transparent evaluation template (baselines, CIs, alert burden) for any future model.

We have run no pilot and have no user or outcome data. No impact figures are claimed.

Validation roadmap (planned)

  1. Retrospective check on open data (ShanghaiT2DM, CC BY 4.0; 15-min CGM).
  2. Serve gradient boosting with SHAP; within-patient chronological evaluation.
  3. Clinician usability review of the dashboard (think-aloud, no patients).
  4. Ethics-approved retrospective study on consented, de-identified data.
  5. Prospective silent-mode study (alerts not shown to clinicians), then a regulatory pathway assessment.
